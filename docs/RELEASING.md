# Releasing Vidra

Vidra distributes official releases and optional prereleases for macOS on Apple Silicon. The first official release is 0.1.0. Public builds must be created by the GitHub release workflow; development FFmpeg binaries must never be distributed.

See [ROADMAP.md](ROADMAP.md) for the version policy and 1.0 acceptance criteria, and [RELEASE-0.1.0.md](RELEASE-0.1.0.md) for the first official release checklist. An official 0.x release has a defined, usable scope while the product continues to evolve; it does not imply Windows or Linux support.

## One-time Apple setup

An Apple Developer Program membership and a Developer ID Application certificate are required for direct distribution outside the Mac App Store. Add these GitHub Actions environment secrets:

- `APPLE_CERTIFICATE`: the Developer ID Application certificate exported as a base64-encoded PKCS #12 file;
- `APPLE_CERTIFICATE_PASSWORD`: the export password for that certificate;
- `APPLE_SIGNING_IDENTITY`: the full Developer ID Application identity;
- `APPLE_ID`: the Apple Account used for notarization;
- `APPLE_PASSWORD`: an app-specific password for that account;
- `APPLE_TEAM_ID`: the Apple Developer team identifier.

Create a protected GitHub Actions environment named `release`, require a maintainer's approval, store the secrets in that environment, and restrict deployment access to release tags.

The release workflow installs Apple's Developer ID G2 intermediate certificate from the official Apple PKI endpoint and verifies its pinned SHA-256 checksum before importing it. Update the checksum only after confirming an intentional certificate change on Apple's PKI page.

## One-time updater signing setup

Vidra verifies every application update with a dedicated updater signing key. The public key is committed in `src-tauri/tauri.conf.json`. Store the encrypted private key and its password only as secrets in the protected `release` environment:

- `TAURI_SIGNING_PRIVATE_KEY`: the complete private key file generated by `pnpm tauri signer generate`;
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`: the password used when generating that key.

Never commit the private key, its password, or an unencrypted recovery copy. GitHub does not allow a stored secret to be downloaded again, so keep a separately access-controlled encrypted recovery copy outside the repository. Losing the private key prevents every installed version that trusts its public key from accepting future updates.

Do not replace the public key directly. Key rotation requires a transition release signed by the current key that ships trust for the replacement key before subsequent releases use it.

## Prepare a release

Source builds of the release engine require these native build tools:

```sh
brew install autoconf automake libtool cmake meson ninja pkgconf nasm
```

1. Update the version in `package.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, and the `vidra` package entry in `src-tauri/Cargo.lock` when the application version changes. A prerelease suffix belongs on the tag only. For `v0.2.0-beta.1`, those files stay at `0.2.0`. `pnpm release:check` accepts the exact tag `v0.2.0` and any tag that starts with `v0.2.0-`, including `v0.2.0-beta.1`.
2. Prepare the relevant entries in `CHANGELOG.md` under an `Unreleased` heading. Before tagging, replace it with the intended release date and align the README status and installation instructions with the release. Preserve the earlier beta history.
3. Run `pnpm check`, `VIDRA_FFMPEG_MODE=release pnpm ffmpeg:prepare`, and `pnpm release:check -- <tag>` on an Apple Silicon Mac, using the intended tag such as `v0.1.0`.
4. Review the dependency and codec licenses in `THIRD_PARTY_NOTICES.md`.
5. Commit the release changes through the normal pull-request process. Merge the reviewed changes before creating a release tag from `main`.

### Development sidecar

On Apple Silicon, `pnpm ffmpeg:prepare` downloads the development archive pinned in `scripts/ffmpeg/dev-archive.json`. It checks the archive SHA-256, checks that the archive contains the corresponding sources, and checks that FFmpeg and FFprobe report the release version. It does not compile FFmpeg. macOS pull-request CI runs that same download.

The archive is produced by the manual **FFmpeg development archive** workflow (`.github/workflows/ffmpeg-dev-archive.yml`). That workflow runs only when a maintainer starts it. It compiles `scripts/ffmpeg/build-release.mjs` on Apple Silicon and uploads one `.tar.xz` and its `.sha256` file to a prerelease tag such as `ffmpeg-dev-8.1.3-r6`. The tag must not start with `v`. It is not a Vidra application release, and the updater workflow ignores it. The workflow uses the default `GITHUB_TOKEN` only. It does not sign or notarize the application.

`scripts/ffmpeg/dev-archive.json` records the SHA-256 of the published archive for the current recipe. When a new archive is published:

1. Open the prerelease and copy the SHA-256 from the `.sha256` asset.
2. Replace the checksum in `scripts/ffmpeg/dev-archive.json` with that value. Leave the recorded recipe fingerprint unchanged unless the recipe itself changed.
3. Commit that pin. Pull-request CI downloads the archive. It does not compile FFmpeg.

`pnpm ffmpeg:prepare -- --build` and `pnpm ffmpeg:release` compile the pinned recipe locally. They need the native tools listed above. Use them when the published archive is not the build you need. Public application releases still compile from the pinned sources in the release workflow.

The development version must match the release FFmpeg version. `scripts/ffmpeg/dev-archive.json` records the recipe fingerprint. The test fails when that fingerprint no longer matches the current recipe, so a recipe change needs a new archive and a new checksum. Update the fingerprint assertion in `scripts/ffmpeg/target.node-test.mjs` only when the recipe change is intentional. After an intentional FFmpeg recipe change, publish a new beta or release candidate and re-validate the engine before an official application release. Publishing the development archive does not publish Vidra.

## Build and publish

Once the release is authorized and preparation is merged, create and push a signed tag from the reviewed `main` commit. For the first official release:

```sh
git tag -s v0.1.0 -m "Vidra 0.1.0"
git push origin v0.1.0
```

The tag after the leading `v` must be a valid semantic version. A prerelease tag may add a suffix, such as `v0.2.0-beta.1`, without changing the corresponding application bundle version `0.2.0`. Its complete value becomes the updater version. An official tag such as `v0.1.0` has no prerelease suffix.

The release workflow then:

- runs the complete frontend and Rust checks;
- builds GPL-enabled FFmpeg and FFprobe, including the dav1d software AV1 decoder and zimg color-conversion library, from pinned, checksum-verified sources;
- verifies AV1 inspection, software decoding, and re-encoding with generated 8-bit and 10-bit MP4/MKV inputs before packaging the engine;
- rejects FFmpeg sidecars that depend on libraries outside the macOS system paths;
- builds, signs, and notarizes the Apple Silicon application and DMG;
- creates a signed `.app.tar.gz` updater bundle and its `.sig` signature;
- creates `latest.json`, validates its platform URLs and signatures, and records the exact release tag as its version;
- verifies the final application with `codesign` and Gatekeeper;
- creates a draft containing the DMG, updater artifacts and manifest, its checksum, FFmpeg corresponding sources, and build configuration. Tags with a prerelease suffix produce a prerelease draft; tags without one produce an official release draft.

Download the draft artifacts and test them on a second Apple Silicon Mac before publication. A prerelease follows the [beta validation checklist](#beta-validation). An official release still needs installation, launch, media inspection, H.264/H.265/AV1 encoding, HDR-to-SDR conversion, HDR preservation, cancellation, and output playback. Confirm that `latest.json` names the release tag and that its `darwin-aarch64` URL and signature match the attached updater bundle. Replace the default draft description with the release's changelog notes, supported platforms, and known limitations. Publish the draft only after those checks pass. Mark a new official release as latest on GitHub. Leave a prerelease unmarked as latest.

## Beta validation

Use this checklist for a prerelease such as `v0.2.0-beta.1`. The bundle version in `package.json`, `src-tauri/tauri.conf.json`, `src-tauri/Cargo.toml`, and `src-tauri/Cargo.lock` stays `0.2.0`. The updater version is `0.2.0-beta.1`. This beta is macOS on Apple Silicon only.

Do not publish the draft until the manual checks below have been recorded. CI does not install the signed application, play media, or exercise the updater.

### Automated in CI

These checks run on pull requests. They do not replace the manual checks on a signed build.

- **Apple Silicon** (`.github/workflows/ci.yml`, job `validate`, `macos-26`): frontend build and tests; `cargo fmt --check`; `cargo clippy --all-targets -- -D warnings`; `cargo test`; `git diff --check`. The job downloads the pinned FFmpeg 8.1.3 development archive. It does not compile FFmpeg, sign the app, or notarize it.
- **Synthetic corpus** (same job, ignored test `conversion_corpus`, `VIDRA_CORPUS_MATRIX=reduced`, `VIDRA_CORPUS_STRICT_ENCODERS=1`): short generated clips encoded through Vidra's argument builder and partial-file publish, then inspected with FFprobe. The reduced matrix covers H.264, H.265, and AV1, MP4 and MKV, HDR10 and HLG sources, and a MOV text subtitle. H.264 output from HDR10 or HLG must be 8-bit BT.709 and must not still be classified as HDR. H.265 and AV1 keep 10-bit HDR. For the HDR10 clip, the macOS sidecar must keep stream-level mastering-display and content-light metadata through those re-encodes. MOV text becomes SubRip in MKV. Source files must be unchanged. This is not playback in a video player, and it does not cancel a running app or write to exFAT, FAT, or SMB.
- **Output safety unit tests** (inside `cargo test`, on Apple Silicon and on Linux where the helpers compile): exclusive rename leaves an existing file in place; a rename that the volume rejects falls back to a check followed by a plain rename only when the name is free; a published claim is not deleted on recovery; shutdown removes an unfinished partial and keeps an existing destination. These tests do not kill a running Vidra process.
- **Linux** (job `validate-linux`, `ubuntu-24.04`): the same frontend and Rust checks, with `VIDRA_FFMPEG_DIR=/usr/bin`. That copy is a development sidecar. The app does not treat it as the release engine unless it reports 8.1.3. The corpus run is a smoke test against Ubuntu's older FFmpeg: missing encoders are skipped, and fast hardware encoding is expected to return `unsupported_platform`. This job is not a Linux release.
- **cargo-deny** (`.github/workflows/cargo-deny.yml`): licenses, advisories, bans, and crate sources with `--locked`. Duplicate crate versions are warnings and do not fail the job.
- **Not in pull-request CI:** signed DMG installation, Gatekeeper, media playback, cancel in the running app, `kill -9` and relaunch, exFAT/FAT/SMB volumes, the update from 0.1.0, or the FFmpeg version shown by the packaged app. The release workflow runs those signature and engine checks only after a signed tag is pushed. This preparation change does not push a tag.

### Manual on an Apple Silicon Mac

Complete these steps on the draft produced by the signed `v0.2.0-beta.1` tag. Prefer a second Mac, without Homebrew or a development FFmpeg. Record the commit or tag, the macOS version, and the result of each item. Leave an item unchecked until there is evidence for it.

- [ ] Install the signed and notarized DMG and launch Vidra. Confirm the app is not the development build.
- [ ] Inspect a representative file and confirm duration, resolution, audio, subtitles, and HDR labeling.
- [ ] Encode H.264, H.265, and AV1, and play each output in a normal player. The source file must be unchanged.
- [ ] Tone-map an HDR10 source and an HLG source with H.264. The outputs must play as SDR and must not still be reported as HDR. Encode the same sources with H.265 and AV1 and confirm HDR is preserved, then play those outputs.
- [ ] Cancel a conversion while it is encoding. The source and any existing destination file must remain. Relaunch Vidra and confirm the unfinished partial is gone.
- [ ] Start a conversion, stop Vidra with `kill -9`, and open it again. The unfinished partial must be removed. A video that had already finished must still be present, including one that had to stay under its partial or numbered name. The source must be unchanged.
- [ ] Encode to exFAT, FAT, and SMB destinations, including a folder that already contains the requested filename when replacement was confirmed. Confirm the finished file is the new video, the previous file was not removed early, and each output plays. The exclusive-rename fallback checks the name and then renames; that check has a very small race.
- [ ] From signed Vidra 0.1.0, leave Stable selected and confirm it does not offer 0.2.0-beta.1. Choose Beta, check for updates, and confirm installation stays unavailable while a conversion is queued or running. After the queue is idle, install the update and confirm Vidra restarts.
- [ ] In the updated app, confirm Settings shows bundle version `0.2.0`, the release link is `v0.2.0-beta.1`, and the FFmpeg row includes `8.1.3`. Run a short conversion. Settings, profiles, history, and the update-channel choice must still be there.
- [ ] Confirm the draft `latest.json` version is `0.2.0-beta.1` and that its `darwin-aarch64` URL and signature match the attached updater archive. The draft must be marked as a prerelease.
- [ ] Publish the draft as a prerelease and do not mark it as the latest GitHub release. Confirm `publish-updater.yml` advances Beta `beta.json` to `0.2.0-beta.1` and leaves Stable `latest.json` on `0.1.0`.

## Update channels

Publishing a versioned release triggers `publish-updater.yml`. The job runs the publication scripts from the default branch, validates the release tag, GitHub prerelease flag, and attached `latest.json` version, then promotes manifests in the rolling `updater-manifest` release:

| Channel | Rolling asset | Eligible versions |
| --- | --- | --- |
| Stable | `latest.json` | Official releases only. Preserves the endpoint used by older Vidra builds. |
| Beta | `beta.json` | Official releases and prereleases, including betas and release candidates. |

The rolling release is only a manifest container; its GitHub prerelease label does not describe the versions in those files. An official release advances both channels when it is newer than their current versions. A prerelease advances only Beta. For example, publishing `0.1.1` updates Stable without replacing Beta's `0.2.0-beta.1`; publishing `0.2.0` subsequently updates both. Equal or older versions never replace an existing channel manifest, and build metadata does not affect version precedence.

Each versioned release still carries its own immutable `latest.json`, updater archive, and signature. Channel publication copies the selected manifest without changing its download URLs or signatures. The workflow must never publish a draft as an update. Malformed manifests or inconsistent release flags fail publication instead of silently changing a channel.

In the app, Stable is the default even for a manually installed test build. The channel preference is stored locally and used for startup checks, manual checks, and installation rechecks. Users opt into Beta in Settings. Switching back to Stable does not reinstall an older version; it waits for a newer official release. The Rust boundary rejects prereleases on Stable independently of the feed contents, and both channels require a newer semantic version and a valid update signature.

Before the first `beta.json` exists, Beta falls back to the legacy `latest.json` endpoint. The legacy endpoint may still name `0.1.0-beta.5` until the first official publication; new Stable clients ignore that prerelease. Already-installed betas continue to use the legacy endpoint and can upgrade to 0.1.0, after which they can select a channel. Creating or merging the channel implementation does not modify existing GitHub release assets.

## Verify an application update

The `v0.1.0-rc.1` prerelease validated software AV1 decoding and a full update from beta.6 through the Beta channel. Follow the [prerelease validation checklist](RELEASE-0.1.0.md#prerelease-validation), including manual installation of beta.6 from beta.5 or earlier.

After an official publication, use the previous signed Vidra releases on a second Apple Silicon Mac to complete the end-to-end updater check. For 0.1.0, cover both the legacy `v0.1.0-beta.5` build and a channel-aware prerelease (beta.6 or rc.1):

1. launch the previous release and confirm that the new version prompt appears;
2. start or queue a conversion and confirm that installation is unavailable;
3. finish or cancel the queue, install the update, and confirm that Vidra restarts;
4. confirm the displayed release tag and run a short conversion with the updated app.

## Rollback

Do not replace artifacts attached to a published versioned release. If a release is defective, mark it clearly in the release notes, publish a fixed version with a new tag, and leave the original source and checksums available for auditability. The `updater-manifest` release is the only mutable release: its `latest.json` and `beta.json` assets point to the newest approved versions for their channels.
